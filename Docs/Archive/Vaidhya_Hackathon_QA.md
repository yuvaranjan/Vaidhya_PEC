# Project Vaidhya — Hackathon Q&A

## Q1. Explain the core technical architecture of your solution and justify your key design choices.

Vaidhya is a two-node system, not a simulated split: a "Village Edge" laptop runs a FastAPI AI service with a local LLM (Qwen2.5-7B via LM Studio) that drives the voicebot, rules engine, and diagnostic-report builder against a local SQLite store, while a "City Central" cloud instance runs the Next.js doctor/pharmacist/analytics portals against a shared Supabase Postgres instance. The two talk over two channels only: an outbox-based sync worker (edge → Supabase, retried every 5s, safe because clinical records are append-only) and HiveMQ MQTT for live doctor↔patient text consults. Everything else — STT/TTS/translation/LLM choice — sits behind a `Protocol`-based provider interface selected by env var, so a cloud dependency (Groq Whisper, edge-tts) can be swapped for a fully local one (faster-whisper, MMS-TTS) without touching business logic.

The key justification is that the edge/central boundary mirrors the real deployment constraint, not hackathon convenience: villages lack reliable connectivity, hospitals don't, so intake reasoning runs where the patient is and specialist/administrative logic runs where the network is. The voicebot's LLM contract also deliberately *selects* from a pre-translated question bank rather than generating free text — this keeps a 7B model from hallucinating clinical questions, makes 4-language support tractable without a translation model in the hot path, and collapses ~90% of turn latency. Provider abstraction and a compare-and-swap doctor-queue claim (Postgres conditional update, no app-level locking) round out the choices that were made for correctness and demoability under a 20-hour budget, not novelty for its own sake.

## Q2. What is the single hardest engineering problem you must solve, and what is your concrete plan for it?

The hardest problem is running clinically coherent, multi-turn, multi-language conversation on a 7B local model within a live-demo latency budget, without it ever hallucinating a dangerous question or stalling on stage. A model that free-composes clinical dialogue is both slow (translation in the hot path) and unsafe (nothing stops it inventing an inappropriate question). The concrete plan is to constrain the LLM's output to a fixed JSON contract — `extracted_facts`, `fired_branch_tags`, and a `next_question_id` that **must** come from a supplied, clinician-reviewed candidate list, with a `free_text_question` field only as a rare escape hatch — enforced via structured output mode, validated with Pydantic, one retry on malformed JSON, then a deterministic fallback (next unasked question in the highest-priority active branch) so the conversation never freezes.

This is paired with a hard latency budget per pipeline stage (~4–6.5s total: STT, LLM, bank lookup at ~0ms for 90% of turns, TTS) and an explicit fallback chain — `EDGE_LLM_FALLBACK=groq` if LM Studio doesn't respond within 20s — so a GPU or model failure at hour 18 degrades gracefully instead of killing the demo. We validated the riskiest link (LM Studio JSON compliance, Whisper on regional languages, edge-tts) in a dedicated hour-1.5–2.5 "risk spike" before any UI work started, specifically so the fallback decision gets made deliberately, not in a panic mid-build.

## Q3. How does your solution scale to a large, real-world user base? Identify the first bottleneck.

The architecture scales horizontally by design at the edge layer: each village/jurisdiction runs its own edge node handling its own patient load independently, with no cross-village dependency for intake — this is the same reasoning that makes it offline-capable, and it means edge-side load doesn't concentrate anywhere. The central tier (Postgres, doctor queue, specialist AI, analytics, Twilio) is the shared resource, but the write pattern into it is append-only sync from many edges plus doctor-driven reads, which is a conventional scale-out problem (read replicas, connection pooling, queue sharding by jurisdiction) rather than an architectural one.

The first real bottleneck is doctor supply, not infrastructure: the queue-claim and jurisdiction-assignment model assumes enough doctors are actively staffing assigned jurisdictions, and nothing in the current design escalates an "Urgent"-tagged patient if every assigned doctor is busy — it just sits tagged in the queue. The second-order technical bottleneck behind that is the specialist-AI and Twilio calls, both third-party API dependencies with per-request cost and rate limits that don't scale for free as consult volume grows; at real scale these need caching, batching, or a self-hosted model tier. We treat the human bottleneck as the more urgent one to solve first, since no amount of infra scaling fixes an unclaimed urgent patient.

## Q4. What makes your approach genuinely innovative compared to existing solutions in the market?

Most rural telemedicine platforms (including government efforts like eSanjeevani) assume a baseline of usable connectivity and degrade to "doesn't work" when it isn't there. Vaidhya's differentiation is that MQTT-text — not video — is the flagship consultation mode: a compressed diagnostic report and short text exchanges are the primary channel, with video/audio as better-case upgrades, not the assumed default. Combined with a genuinely local LLM running the entire intake conversation (vitals-aware branching, dynamic on-demand exam requests, report generation) with zero internet dependency, the core clinical workflow is designed to survive exactly the network conditions rural India actually has, rather than the network conditions a demo environment has.

The second differentiator is that the AI is structurally constrained rather than open-ended: the voicebot can only select from a clinician-reviewed question bank, the branching rules are a data table with a restricted comparison-operator grammar (no `eval`, no free expression language) so a non-engineer can audit or edit them, and every specialist AI opinion returns a structured confidence score plus evidence trace instead of prose. This makes the system's clinical behavior auditable and editable without a redeploy — a materially different design posture from black-box LLM chat wrapped around a form.

## Q5. Which parts of your repository are functional today versus still planned, and how do you know?

As of today, the repository contains architecture and planning documents only — the product contract, technical architecture, and hour-by-hour build plan — with no `apps/`, `services/`, or `db/` code committed yet. I know this directly from the repository contents: it holds six markdown documents (architecture v2 through v5, the technical architecture, the implementation plan, and an internal honesty Q&A) and no application source tree. The 20-hour build has a locked hour-by-hour schedule with two mandatory integration checkpoints (intake reaching the doctor queue at H8–H9, and the MQTT consult working end-to-end at H14–H15) and a pre-agreed cut ladder, but none of those hours have started yet against this snapshot of the repo.

What's genuinely decided and de-risked, rather than aspirational, is the technical contract itself: schema (`db/001_schema.sql`), provider interfaces, the MQTT topic/payload shape, and the compare-and-swap queue-claim query are all fully specified down to working SQL and code sketches in the architecture docs, which is what lets four people build against frozen contracts in parallel instead of discovering integration mismatches at hour 18. Our own internal Q&A prep document is explicit about current gaps (no MQTT transport encryption, no doctor credential verification, no patient consent step before webcam capture) — those are documented as known, unbuilt limitations rather than claims of completeness, which is the most honest signal of what's real versus planned right now.
